# 6.1.3 锁单入口与可靠增量更新设计

状态：用户同意方向，进入实施计划审核；不代表代码、部署或发布已经完成。

## 1. 目标与事实边界

用户目标：普通锁单、脚本锁单都能进入目标详情，点击一次提交按钮，确认待付款订单后停止；详情页锁单标注推荐。全面排查部分用户更新失败，后续优先只下载变化文件，仍由用户确认更新。

当前基线是已发布的 6.1.2。项目不是 Git 仓库；采用基线文件快照、完整 dist 备份和不可覆盖发行目录留证，不声称已经提交 Git。

已证实的事实：

- 6.1.2 修复已退出进程在 Toolhelp 快照中被误认为身份未知的问题；两条真实旧版升级路径通过。不能因此声称所有客户更新故障已解决。
- 现有普通/实验购买加速最终经过 auto_pay 分支，默认停在支付前；auto_pay 分支等待支付成功，不等于用户需要的待付款锁单确认。
- 现有详情页模式有一次提交和新待付款订单确认流程，可以复用其成功判定，而不是复制自动支付后续流程。
- 6.1.1 到 6.1.2 的 1809 个发行文件中仅 5 个变化，当前仍下载 73,179,968 字节全量包。变化文件未压缩合计 21,742,102 字节；不能把这个未压缩数当作未来增量 ZIP 的实测体积。
- 当前下载器设置较短的单次读取超时，网络异常立即结束；需要在慢网、抖动和暂停收包条件下复现，不能仅凭代码推断它就是每个客户的根因。
- 客户截图存在 360 压缩临时目录启动的情况；尚缺其新版具体失败记录。

不作出的承诺：固定抢单成功率、首次提交绝不扣款、所有环境均可自动更新。首次按钮行为取决于平台及账号设置；程序只保证不主动继续后续付款流程或绕过验证。

## 2. 锁单界面与行为

### 2.1 命名和适用范围

保持当前布局：

- 极速购买 → 普通锁单。
- 实验极速模式 → 脚本锁单；说明保留“页面事件可能不被平台接受”。
- 详情页锁单 → 详情页锁单（推荐）；说明“提前进入详情，减少开售后的跳转；确认待付款后停止”。不写未经统计的“成功率高”。

移除秒杀场景重复的“进入结算页后自动点击支付”控制；批量下单的自动支付及多账号行为不变，在批量场景继续独立显示和使用。

保留现有选框结构，明确生效优先级：详情页锁单 > 脚本锁单 > 普通锁单。界面和启动日志显示实际生效模式，避免多个选框勾选后含义不清。

### 2.2 一次提交合同

三种锁单模式共用成功判定与禁止重复提交的状态规则，但保留入口差异：

1. 普通锁单：库存事件后原生点击预绑定商品控件，进入详情。
2. 脚本锁单：库存事件后一次页面购买事件进入详情；平台未接受时停止，不自动补一次原生购买点击。
3. 详情页锁单：提前进入详情等待提交控件，保持现有安全刷新和人工验证恢复行为。
4. 进入详情后，定位唯一目标、确认规格、金额和数量，再原生点击一次“支付”提交。脚本事件不应用到最终提交按钮。
5. 以新的订单号及明确待付款状态确认锁单。提交前记录已有订单，旧待付款订单不能成为本轮成功证据。
6. 确认后停止任务，保留浏览器供用户处理付款；不关闭/放弃支付，不进入 wait_for_payment_success，也不切换账号继续下单。
7. 点击超时、结果不明、库存丢失、控件身份变化或验证出现时按现有安全规则停止/暂停；提交后不重新点击或继续刷新抢单。

规格与价格不能为速度牺牲；金额暂为零、详情被回收成另一商品、多个支付控件、数量不为 1 等不满足提交条件时不得提交。监控窗口截止检查适用于三种模式的最终提交，不仅详情模式。

测试模式只报告命中，不触发购买/支付事件，不创建或锁住真实订单。日志区分“发现库存”“打开详情”“已提交待确认”“锁单确认”“未确认/停止”，并报告阶段耗时，不能将“点击成功”写成“锁单成功”。

### 2.3 配置迁移和确认

旧速度开关可保留，但旧真实任务不能无提示地获得新增提交能力。升级后首次使用普通/脚本锁单，启动确认明确说明新行为；拒绝确认不启动任务。之后每次真实下单仍保留账号、商品、金额和潜在扣款风险确认。

秒杀锁单不沿用 auto_pay 的后续付款分支；批量模式仍按原 auto_pay 配置执行。任何配置迁移不自动开启真实任务、不绕过激活、不删除账号及商品设置。

## 3. 更新故障全面检查与可观察性

### 3.1 阶段和预检

阶段：检查清单 → 确认方案 → 基线/目录预检 → 下载 → 校验/组装 → 更新器接管 → 等待旧实例退出 → 备份/替换 → 新版启动确认 → 提交或恢复。

尽量将可判定的失败移到下载之前：持久安装目录、写入权限、剩余空间、未完成更新、用户资料是否与管理根目录重叠。区分“临时目录”证据，不能仅因用户使用 AppData 或自定义文件夹就全部拒绝。

对于已明确的压缩包预览临时目录（例如截图中的 360zip 临时展开位置），停止原位更新并指导完整解压到固定文件夹；不自动猜测搬迁用户软件或清除临时目录。

保持 6.1.2 的退出确认修复。身份未知的存活进程不能简单略过；权限异常显示 PID 和系统错误，并说明未替换文件。检查不同安装目录、多实例、管理员权限混用、启动/退出竞态及文件占用。不得自动提权、强杀进程或关闭杀毒软件。

### 3.2 诊断和恢复提示

新增有上限的结构化更新日志及“导出更新诊断”：产品/协议版本、目标序号、当前阶段、时间/耗时、包类型与字节数、系统错误码/PID、安装位置、事务状态和恢复结果。导出时脱敏用户目录名称，不记录 Cookies、登录存储、激活卡密、私钥、认证头或握手令牌。保持本地导出，不自动上传。

无法升级的旧客户端先收集错误截图、对应 result.json，以及存在时的 journal.json 并脱敏；不要求客户发送 job.json、激活文件或浏览器资料。导出诊断不能成为旧版升级必须满足的前置条件。

错误分类至少包括网络、清单签名、包哈希、基线文件、空间/权限、进程、文件占用、接管、替换、启动确认和恢复。通过阶段证据归因，缺记录的客户报告标为待确认，不猜测“全是网络”或“全是权限”。

只有已经产生有效 journal 的事务才显示对应恢复入口。未开始替换时明确“未替换文件，旧版保留”，不得把不存在的 journal 路径作为唯一解决方法。已经替换但未确认启动时，保留事务/备份，指引关闭该目录实例后恢复。

### 3.3 下载可靠性

连接、网络空闲与总任务时限分开管理；短时未收到一个数据块不能直接等同整次更新失败。取消检查保持有界，更新期间禁止新监控/下单/登录/测速任务。

下载使用不可变官方 URL，允许网络中断后有上限重试，并支持同一包的 Range 续传：严格检查 206 的 Content-Range 起点、总长度及响应编码，续传标识绑定签名中的包路径、大小和哈希。服务器返回 200 时，从零重启，不拼接两个完整响应；格式异常、重定向或内容超限停止。每次续传建立新连接，不复用已经超时的响应文件对象。

任何部分下载都不是可安装文件；完成后必须整体哈希校验。签名/哈希错误不以“网络重试”掩盖，也不安装未校验内容。用户看到阶段、进度、速度和错误原因，而不是仅看到“失败”。

### 3.4 无法原位更新时的备用安装

用户无法提供客户诊断文件，验收不以取得这些文件为前提。新增证据包括“资料目录重叠”及“进程仍运行但身份不能确认；未替换文件”两种提示；后者说明不能只复用 6.1.2 的退出竞态修复。空白登录资料路径在启动配置和更新保护检查中必须统一使用默认目录，不能将空字符串解析成当前目录。

对确实不能安全原位更新的情况，提供完整包下载和新目录安装入口。下载仍须签名及哈希验证；用户选择新的空白、持久、可写目录，完整解压而非只复制 EXE。保持原安装和浏览器资料不动，启动前明确退出旧软件；权限异常不能通过跳过实例检查解决。验证新目录全部文件后提供打开文件夹/启动新版的用户操作，不能自动恢复下单任务。

旧客户端在下载或目录预检阶段失败，尚无法运行新版修复代码，因此必须提供官方完整包手动安装说明，不能承诺仅服务端调整即可让所有旧客户端自动更新。备用安装和原位升级均测试资料保留；用户原先自定义登录目录继续明确指向原目录，不偷偷复制或改写登录资料。

## 4. 文件级增量更新架构

### 4.1 全量协议保留

现有 protocol 1 的完整清单、全量 ZIP、latest.json 和旧请求结构保持兼容。6.1.0～6.1.2 首次升至 6.1.3 仍用完整包，并由包中新版更新器接管；6.1.3 具备增量能力，后续发行优先使用增量。

首版增量只支持一个基线：上一个正式版本。跨多个版本、基线不支持或增量不划算时，明确提示完整包方案，不要求串行安装每个历史版本。

增量按完整文件变化，而不是二进制字节补丁；EXE 变化时仍下载完整 EXE。适用于减少未变化运行库的重复下载，不保证每次更新都很小，也不降低磁盘备份需求。

### 4.2 签名与元数据

继续使用独立更新签名密钥，不使用授权签名私钥。新增严格定义的 protocol 2 增量方案和请求；旧 protocol 1 的验证与请求不因增量放宽。

增量方案绑定产品、平台、基线版本、目标版本和同一个正式发行序号、完整目标清单的 SHA256、增量包路径/大小/哈希、变化文件列表（路径/大小/哈希）。完整目标清单仍独立验签并列出最终所有发行文件。

变化列表与完整目标清单必须一致；基线未满足时不尝试“猜测”重用。路径穿越、大小写重复、链接/重解析点、管理范围外文件、压缩炸弹及清单外文件继续拒绝。增量重放和跨版本/跨产品拼接必须拒绝。

### 4.3 本地组装与独立更新器

1. 用户确认增量方案后，在安装目录下创建独立事务工作区，不直接覆盖当前程序。
2. 对目标清单中未包含于增量包的文件，逐个校验当前安装文件与目标 SHA256/大小相符，复制到完整暂存目录；不得用硬链接使暂存和安装文件互相影响。
3. 解包经验证的新增/变化文件；完整暂存目录仅按目标清单建立，旧版已移除的受管理文件不会被复制到新版本。
4. 再次验证全部暂存文件、类型、数量和哈希。校验期间文件被修改、不可读取或缺失，停止增量并给出重新选择完整包的提示；不能静默扩大下载量。
5. 新版独立更新器重新验证完整目标签名、增量签名和包、请求身份及全部暂存文件，然后才可等待实例退出并安装。
6. 沿用现有五个管理根目录的备份/替换/恢复事务和新版启动确认，账号资料/设置/激活文件位于保护范围，不能覆盖。

关键兼容限制：本地组装的完整目录不是服务器原全量 ZIP，不能假装它具有原全量包哈希。protocol 2 使用经签名的目标文件目录验证；不能简单绕过现有 validate_archive，也不能要求不同机器重新压缩出与服务器逐字节相同的 ZIP。

全量协议 1 仍验证完整 ZIP。新更新器接受严格的两种请求结构；老客户端的请求仍是协议 1。新客户端的增量请求含目标清单和增量方案/包引用，恢复时再次验签，保存足够资料以在断电后恢复，不依赖再次联网。

### 4.4 服务端发布与兼容接入

为每次正式发行同时保留完整 ZIP，支持直接下载和旧客户端。新增增量包/方案的精确白名单路由；不开放整个更新目录或私钥路径。

端点约定：`/updates/stable/incremental.json` 为当前目标的签名增量索引；`/updates/releases/<target>/incremental-<base>.json` 为不可变的签名方案；`/updates/releases/<target>/DYLiveAssistant-<base>-to-<target>-windows-x64.zip` 为增量包。版本段严格限制为已有版本格式，不允许任意文件路径。完整 `/updates/stable/latest.json` 继续服务旧客户端。客户端只接受与已验签完整目标版本/序号相符的增量方案；404/无适用基线可以选择全量，签名异常必须停止。

索引只承载本次目标及上一个正式基线的方案引用/哈希，方案包含变化文件，不重复嵌入每个历史版本的完整清单，以维持元数据大小上限。目标完整清单以已验签的完整 latest.json 原始字节 SHA256 绑定，并随事务保存。

先发布并校验不可变版本资源和对应增量方案，再切换完整 latest.json 作为正式发行可见标志。新旧索引暂时不匹配时不得混合安装，应重新检查或提示全量；发布失败不覆盖已经存在的版本目录。

6.1.3 向 6.1.4 的增量能力通过未正式公开的测试发行验证，不为了测试向真实用户发布一个虚假的新版本。版本 6.1.3 发布后将为下一正式版本建立基线。

如果新增路由/工具需要服务器配置变更，先完成备份和配置检查；若需重建 blog-frontend、可能中断博客，另外征求许可。不得改博客内容、授权数据库或授权私钥。

## 5. 测试与发布门槛

### 5.1 锁单

以全本地模拟商品页验证三个模式：缺货→短库存→待付款；点击支付恰好一次；新订单才能确认；库存/按钮切换、金额0/不符、规格默认/多选、数量变化、窗口结束、验证码、脚本事件拒绝、点击结果不明、旧订单残留、干运行零点击。检验旧配置确认和批量行为不变。记录上架→购买→提交→待付款确认的耗时，不将本地结果写成真实平台成功率。

### 5.2 更新

覆盖正常/低速/间歇暂停/断网/代理和重定向、正确及异常 Range、磁盘不足/只读目录/临时展开位置、多个安装目录实例/权限不足/退出竞态、签名/哈希/基线篡改、文件删除和新增、组装中源文件变化、失败恢复、断电和新进程不确认。

实际 EXE 验收：6.1.0/6.1.1/6.1.2 → 6.1.3 全量；6.1.3 → 私有测试目标增量及全量回退。确认最终管理文件等于目标发行、用户数据不变、旧备份可恢复且无自动下单。另测试新 helper 对旧请求兼容。

完整回归通过、独立审查的严重问题解决、发行 EXE 内嵌代码与源码一致后，才进行正式签名发布。发布后通过官方 HTTPS 验证完整/增量资源、缓存头、签名/哈希和博客/授权健康，再替换本机 dist 并验证实际启动。保留完整旧 dist。

## 6. 交付与审核顺序

交付：新版 dist 与完整 ZIP、服务端兼容发布工具/路由、协议和恢复测试、简洁手册、脱敏更新诊断导出、实测增量体积/耗时对比及备份位置。

推进顺序：用户审核本设计 → 编写分阶段实施计划 → 用户审核计划并选择执行方式 → 测试驱动实施 → 独立审查与发布验收。当前不改动 6.1.2 的发行服务。

客户故障归因仍需要对应新版截图/脱敏诊断。没有客户记录时，可以交付覆盖上述故障的测试与诊断能力，但不能声称已证明每一个客户的具体失败原因。
