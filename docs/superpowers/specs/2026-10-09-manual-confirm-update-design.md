# 手动确认更新：设计方案

日期：2026-10-09。状态：用户已确认本书面设计；实施计划待确认。计划确认后才开发或部署。

## 1. 目标与边界

用户在开发机修改软件，测试、打包并明确发布后，已安装的软件可以发现新版，由使用者选择更新。未经确认不下载程序包、不关闭软件、不替换文件。更新不进入下单热路径，不中断秒杀、批量任务或登录。

第一版使用现有腾讯云服务器和 https://license.txblog.cn/updates/，不新增域名、发布管理网站或远程代码执行接口。保留联网及旧离线激活。更新检查与激活校验互相独立：更新网络失败不得阻止正常使用旧版。

不包含强制升级、静默安装、增量补丁、跨平台更新、自动取消订单、自动关闭用户浏览器或支付测试。现在已经分发的旧 EXE 不支持更新，用户必须手动安装一次带更新功能的新发行包。

## 2. 方案选择

采用完整程序包下载 + 独立更新程序。当前 PyInstaller 是文件夹发行，EXE 依赖 `_internal`，只下载主 EXE 会造成版本混用。完整包比增量补丁更容易校验、回滚；独立程序从安装目录外运行，避免替换运行中的自身。

备选为提示后由用户手动解压覆盖，实现简单但容易遗漏依赖；不采用。增量补丁及强制更新不在第一版范围。

## 3. 用户界面与忙碌约束

主窗口显示当前版本，并提供“检查更新”。首次带更新功能的发行版编号设为 6.1.0，后续采用递增的三段数字版本，如 6.1.1、6.2.0；不从旧 ZIP 文件名推断运行版本。

成功启动主界面后仅在空闲时后台检查一次。启动时忙碌则跳过本次自动检查，不周期轮询。检查结果经现有 UI 队列交回主线程，不阻塞界面。自动检查失败只显示简短状态，不反复弹窗；手动检查失败显示可理解的错误。没有新版本就显示“已是最新版本”。

发现新版显示：当前版本、新版本、更新说明、包大小，以及“立即更新 / 暂不更新”。“暂不更新”不下载，本次软件会话不再次自动提醒；手动检查仍可打开提示。用户确认后显示下载进度、取消下载按钮。下载期间禁止启动监控、批量、登录或另一项更新；也不与网络测速竞争。

运行任务、登录浏览器尚未退出、网络测速或正在退出时禁止下载和安装，提示先结束相关操作，绝不自动停止它们。读取更新结果到用户点击确认之间也重新检查忙碌状态，消除竞争窗口。下载取消或失败立即释放界面限制。正在下单时不发起更新网络检查；更新按钮可提示“任务结束后再检查”。

Python 源码运行模式可以显示版本/检查结果，但不执行 EXE 原位更新，明确提示使用发行版。

## 4. 组件边界

| 组件 | 责任 |
| --- | --- |
| 版本与公共配置 | 产品标识、当前版本、Windows x64、固定 HTTPS 更新源、更新签名公钥；无密码和私钥 |
| 更新协议校验 | 版本比较、签名验证、字段/地址/大小约束、包与文件哈希、ZIP 安全校验 |
| 更新客户端 | 限时检查、确认后流式下载、进度、取消、暂存和安装请求；不碰授权及账号文件 |
| 独立更新程序 | 二次校验、等待原进程正常退出、事务备份/替换/恢复、重新启动软件、保存结果 |
| 发布工具与服务器配置 | 白名单打包、签名、不可变版本上传、最后切换最新版索引、现场验收 |
| GUI 接入 | 展示、确认和忙碌互斥；不改变 AutomationRunner、订单或账号队列语义 |

组件按独立模块实现，避免把下载、ZIP 解压和文件事务塞进 GUI 或授权代码。

## 5. 发布协议与可信来源

客户端固定获取 `/updates/stable/latest.json`，这是有长度限制的签名封装。封装包含 `key_id`、结构化 `payload` 和 Ed25519 签名；签名覆盖带产品/协议用途域标识的确定性 JSON 字节，不接受未签名的兼容格式。

签名内容包含协议版本、产品标识、平台、三段版本号、递增发布序号、UTC 发布时间、说明、固定源下不可变 ZIP 路径、下载字节数、ZIP SHA256、逐文件路径/大小/SHA256、更新程序协议要求。首次协议版本为 1。拒绝未知协议、非本产品/平台、无效或重复字段、不合法版本、非递增版本、包信息和文件清单不一致。

客户端只接受固定 HTTPS 源和 `/updates/releases/` 下的包，不接受 URL 用户名密码、查询凭据、跨源跳转、HTTP 降级、任意外部地址或禁用 TLS 校验。更新元数据不携带卡密、登录资料或用户机器信息；下载无需管理员登录。已经验证过的最高发布序号保存在更新状态中，拒绝较旧索引；本地数据被人为恢复不属于绝对防回放保证。

更新签名使用独立密钥，不复用授权凭证私钥。私钥只存服务器专属非公开、受限目录；本机与发行包仅含公钥。发布工具在服务器通过受控命令签名，不将签名做成公网 API。第一版单个更新公钥，密钥损坏或撤销需要手工引导安装新可信发行版，不宣称支持透明轮换。

清单最大 2 MiB，ZIP 最大 512 MiB，解压总大小最大 2 GiB，文件最多 15000。检查请求限时 10 秒；下载有连接/读取超时和总时限 10 分钟，取消后停止读取，不在后台无限重试。先检查下载/解压/备份所需空间，不足时保留旧版。

## 6. 发行文件与用户数据

更新包根目录仅包含：`DYLiveAssistant.exe`、`DYLiveUpdater.exe`、`_internal/`、`用户使用说明.md`、公共 `release-info.json`。包不包含旧 ZIP、诊断、浏览器目录、账号记录、激活文件、私钥或开发工具。新旧版本均必须拥有明确的程序文件边界。

更新只处理这五类程序文件，其他安装目录内容保留。默认 `%LOCALAPPDATA%/DYLiveAssistant` 内的账号、登录、激活、设置和诊断不移动、不覆盖、不迁移格式。新版本必须兼容这些数据；第一版更新不做数据迁移。用户自定义登录资料若与受管程序路径重叠（例如放在 `_internal` 内），拒绝自动更新并提示先手动迁出，不能因更新丢失登录资料。

解压先校验路径再创建文件，拒绝绝对路径、`..`、盘符、UNC、NTFS ADS、保留设备名、链接、目录联接、大小写重复或文件/目录冲突。拒绝清单外文件和缺失文件；解压完成逐文件校验哈希。原安装、备份和暂存路径也检查真实路径及重解析点，不能把更新范围扩展到上级、工作区根或用户数据目录。

## 7. 安装事务与恢复

流程：检查 → 用户确认 → 下载并验证 → 解压验证 → 确认空闲及目录可写 → 外部更新程序接管 → 软件正常退出 → 备份 → 替换 → 校验 → 重新启动。

1. 每次更新创建独立暂存目录及事务 ID；以规范安装路径为单位使用 Windows 跨进程锁，禁止并发安装。外部更新程序复制到受限暂存路径后运行，不使用待替换目录中的共享运行依赖。
2. 主程序与更新程序先完成就绪握手，再正常保存设置、关闭。更新程序等待原进程及该安装目录其他实例退出，最长 30 秒，不按名字杀进程。未退出或文件被占用则停止，保留旧版并提示。
3. 更新程序独立验证签名和包/文件哈希，不能仅相信 GUI 传来的版本、目标路径或“已验证”标记。目标必须是启动它的那个发行目录，不能由网络清单指定。
4. 在安装目录同卷的专属事务目录保存全部旧受管文件，以持久化事务日志记录每次移动的准备与完成。非受管文件不移动。所有路径与完整旧备份可验证后才替换新文件，不先删除旧 `_internal`。
5. 替换后核对完整受管清单。任一步失败执行可重入恢复，保留失败的新文件及日志；恢复成功重新打开旧版。磁盘不足、目录只读或权限不足时不自动提权。
6. 重新启动新软件，在激活界面或主界面完成首次可用事件循环后发送有事务令牌的启动确认，最长 30 秒，不需要联网激活或输入卡密即可确认激活界面可启动。启动失败/超时，若新进程已经退出则恢复；若它还活着，不强杀或带锁替换，提示本人关闭并由恢复工具继续。
7. 成功后记录安装版本和结果，保留最近一次完整备份供人工恢复。启动确认只代表程序能启动，不等于下单成功或全部业务健康。新程序不得自动恢复监控、下单、登录或支付。
8. 突然断电/退出后，从持久化事务识别不完整安装；提供安装目录外的恢复启动入口。无论主 EXE 是否还能启动，都可运行恢复工具依据日志继续恢复。需要验证恢复工具自身的来源和版本，不能只提供放在可能缺失的 `_internal` 内的恢复代码。

备份、暂存和恢复日志只用本次明确的专属路径；第一版不自动递归清理历史发行或用户文件。失败信息只包含版本、阶段和脱敏错误，不输出激活数据、浏览器 Cookie 或私钥。

## 8. 服务器与发布操作

公网 Nginx 为 `/updates/` 增加独立静态只读路径，禁用目录浏览。`stable/latest.json` 禁止长缓存，版本目录不可变并可长期缓存。与授权 `/api/v1/`、管理员入口和博客路由分离，不将大包下载送入授权后端限流。

新增文件放专属 `/opt/dy-updates`，不覆盖 `/opt/dy-license` 的数据库、授权密钥或博客目录。先只读核对现场 Nginx/Compose/挂载和证书路径；若新增挂载需要重建博客前端，提前说明短暂中断并单独获得同意。仅校验通过的 Nginx 配置可 reload，不重建数据库或博客后端。

维护者发布流程：

1. 修改软件，完整测试，设置新版本号和简短说明。
2. 白名单打包，校验不含秘密，验证主 EXE 和更新程序可运行。
3. 上传至新的不可变版本目录，以临时文件接收，校验包及文件清单；同一版本已存在则拒绝覆盖。
4. 使用独立更新签名私钥生成签名索引；确认文件可用后最后原子替换 `stable/latest.json`。保留上一索引用于撤回发布，不先公开指向未完成包的索引。
5. 用正式域名从客户端验证签名、下载内容和版本提示，并检查授权网站、原博客仍正常。

修改本地代码或重建 dist 不自动公开发布；上传与切换索引必须是维护者明确选择的操作。撤回只停止推广坏版本，不静默降级已安装用户；修复必须发布更高版本。提供简明发布说明与工具，不新增发布管理网站。

## 9. 验收与测试

- 更新提示：无新版/新版/网络失败/签名错误/错误平台，暂不更新没有包下载。
- 忙碌边界：秒杀、普通批量、多账号、人工验证保留浏览器、登录、测速期间不下载或替换；确认前后竞争状态再次核对。
- 用户资料：账号、设置、浏览器资料、联网与离线激活、非受管安装目录文件在成功和失败场景均保持一致。
- 包安全：哈希不符、截断、跨源重定向、签名伪造、回退索引、ZIP 路径穿越、链接、重复文件、压缩炸弹、过大文件均拒绝且不改旧版。
- 原位安装：用独立临时安装目录模拟升级、文件占用、权限不足、写入故障、每个事务阶段中断、可重入恢复和并发；不借用用户真实运行任务。
- 真正打包测试：旧带更新 EXE → 下载新完整包 → 新版启动确认；失败版 → 恢复旧版；取消/只测试场景不产生真实订单。首次版本仅由人工安装。
- 完整项目回归、独立代码审查、发行内容/源码一致性检查及现场 HTTPS 静态源验证。测试环境已有 Tk 跨线程循环回收问题，普通发现运行和主线程回收测试器结果分别记录，不掩盖中断。
- 秒杀性能：证明更新代码不在扫描、开售检测、购买或支付热路径中，没有新增授权/更新网络请求或磁盘等待。

不能用沙盒测试宣称真实平台下单成功率、真实服务器上线或终端用户更新成功；分别用现场证据验收。

## 10. 实施门槛

这份文档只记录设计。本地不是 Git 仓库，文档保存在工作区，不声称已提交 Git。用户确认本书面设计后再编写分步实施计划；用户确认计划与执行方式后才开始实现。正式服务器部署与发布需要按第 8 节核对现场并明确范围。
